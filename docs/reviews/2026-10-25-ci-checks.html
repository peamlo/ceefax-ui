Areas covered: security, readability, static checks, bundling, token exposure, accessibility, dead code. The checks are ordered by how much they protect the artefact consumers actually install.

Cost & solo-maintainer fit

Everything proposed costs €0 for this repo. That depends on two facts: the repo is public (ADR-0002), so GitHub Actions minutes on standard runners and GitHub's security features are free, and every tool below is open source and runs inside Actions. For a solo maintainer, the real cost is time: setup, noisy PRs, and false positives. The last column rates that.

Deliberately not proposed (paid or high-upkeep)

  • Chromatic / Percy visual regression: freemium snapshot quotas, and baseline review is a chore for one person
  • Snyk / Socket: free tiers exist, but Dependabot and dependency-review cover the same ground for free
  • SonarCloud: free for public repos, but overkill for about 600 lines of CSS and JS
  • CodeQL: free on public repos, but there is little JS to analyse. Add it later if src/elements grows.

Solo-maintainer rules of thumb

  • Few required checks. Make build, lint and test-storybook required. Leave a11y-demo, knip and docs advisory until they have been quiet for a while.
  • Shift left. Run Prettier and Stylelint in the existing husky hook (lint-staged) so CI failures are rare surprises
  • One workflow, parallel jobs. A single ci.yml with a shared npm ci cache is easier to keep current than six files
  • Batch the bots. Monthly grouped Dependabot, plus auto-merge for patch-level devDep bumps once tests pass
  • If the repo ever goes private, the free tier changes: Actions minutes become capped (2,000/month), and secret scanning and dependency review need GHAS

1 · Build & package gate (bundling)

Strong

Files: package.json (build, files, exports, sideEffects), postcss.config.js, fonts/, new .github/workflows/ci.yml

Problem

The thing consumers install (dist/*.css, src/elements/*.js, fonts/) is never built or packed in CI. Each packaging regression so far was found by hand after merge. The tarball also includes about 560 KB of .ttf files that no stylesheet references (only the woff2 are in @font-face). And because postcss-url copies fonts to dist/fonts while files also lists fonts, the woff2 files probably ship twice. That needs confirming with one npm pack.

Solution

Add a build job: npm ci → npm run build → npm pack --dry-run --json, then run publint on the result. Add a small assertion script that checks every exports target exists in the tarball and every url() in dist/*.css resolves to a packed file. Also import each ./elements/* subpath in a clean temp project to prove it resolves and registers its custom element.

Benefits: the published package gets checked where its bugs have actually been. #37 and #39 would both have failed here before merge. The check runs against the packed tarball (what consumers install), not against src/.

2 · Size budget (bundling)

Strong

Files: dist/index.css, dist/tokens.css, src/elements/index.js, cf-canvas.js, cf-loader.js, new .size-limit.json

Problem

The library promises to be a CSS-first core that stays small, with JS strictly opt-in (ADR-0001). Nothing measures that. The output is not minified either: the PostCSS chain has no cssnano.

Solution

size-limit (or compressed-size-action for a PR comment) with brotli budgets per entry, e.g. index.css ≤ N KB and elements/cf-loader ≤ 1 KB. Also add a budget asserting ./css pulls in zero JS. Whether to minify dist is a separate decision for you; the budget is useful either way.

Benefits: every PR shows its size delta, so growth that would break the CSS-first promise in ADR-0001 is visible when it happens.

3 · Stylelint that enforces the contract (static checks + readability)

Strong

Files: src/**/*.css, new stylelint.config.js; plus ESLint + Prettier for src/elements, stories, .storybook

Problem

The contract in AGENTS.md (no state-modifier classes, one cf-* namespace, no --cf-base-* outside the token layer) is enforced only by review, plus the Token layering story for the last rule. The CSS is also written as minified one-line rules (colors.css, typography.css), so diffs are hard to read.

Solution

  • selector-class-pattern: ^cf-[a-z]+(-[a-z]+)*(__[a-z]+)?$ makes cf-btn--disabled a lint error
  • custom-property-pattern: ^(cf|_)[a-z-]+ keeps the token namespace consistent
  • declaration-property-value-disallowed-list bans raw hex outside src/tokens/
  • ESLint flat config with eslint-plugin-wc and no-unsanitized (both custom elements set innerHTML; it is static today, and this keeps it static)
  • prettier --check for formatting
ADR-0006 / ADR-0008 note: this does not replace the Token layering guard story; stories remain the test surface. Lint is a faster, in-editor complement. Keep the story as the gate.

4 · Public-surface diff (design-token exposure)

Strong

Files: dist/index.css, dist/tokens.css, new api/surface.json snapshot

Problem

The library's public interface is its --cf-* custom properties, its cf-* classes, and its data-* values. The --ceefax-* → --cf-base-* rename (#25) was breaking, and only the ! in the PR title recorded that. Nothing would catch an accidental removal or rename.

Solution

A script parses the built CSS with PostCSS and extracts the sorted set of exposed custom properties, semantic classes, and [data-*="…"] values. It diffs that set against a committed snapshot. Additions are fine once the snapshot is updated. A removal fails unless the PR title carries ! or a BREAKING CHANGE footer. The lint-title job already reads the title, so it can perform that check.

Benefits: the semver promise lives in CI alongside the existing commitlint gate, and reviewers see the surface change as a readable diff.

5 · Supply-chain & secret hygiene (security + token exposure)

Strong

Files: .github/workflows/*.yml, new .github/dependabot.yml, future release.yml

Problem

  • Third-party actions are pinned to mutable tags
  • storybook-tests.yml has no permissions:, so its GITHUB_TOKEN gets the repo default scope
  • npx --yes http-server / wait-on install unpinned packages at CI time, bypassing the lockfile
  • No dependency audit; there are about 800 locked packages, almost all from Storybook
  • Publishing presumably uses a long-lived npm token stored somewhere

Solution

  • zizmor to lint workflows (it flags unpinned actions, excessive permissions, and template injection)
  • Pin actions by SHA; Dependabot for github-actions + npm
  • actions/dependency-review-action on PRs (license + vuln gate) and npm audit --omit=dev. Prod deps are currently empty, so this stays green and catches the day one is added.
  • Enable GitHub secret scanning + push protection (free for public repos). Optionally add gitleaks in CI.
  • A release.yml using npm trusted publishing (OIDC) with --provenance, which removes the long-lived npm token
  • Move http-server/wait-on into devDeps

AFTER

6 · Accessibility beyond Components/* (accessibility)

Worth exploring

Files: demo/index.html, demo/screen.html, .storybook/test-runner.js, src/elements/cf-loader.js

Problem

axe runs only on isolated contract stories. The demo pages, which are the closest thing to a real consumer page (whole-page landmarks, heading order, the page shell plus fastext together), are never audited. Reduced motion and forced-colors are claimed but not asserted.

Solution

  • A Playwright + @axe-core/playwright job (or pa11y-ci) over demo/*.html, served raw, in both themes, with a full ruleset including landmark-* and heading-order
  • In postVisit, add page.emulateMedia({ reducedMotion: 'reduce' }) and assert <cf-loader>'s cursor has animation-name: none
  • forcedColors: 'active' run to check that focus inversion stays visible
  • Optional: Lighthouse CI against the Pages deploy
ADR-0006 note: keeping Foundations/Layout stories out of the gate is already decided and tracked. This proposal leaves those stories alone and adds a different surface, the demo pages.

7 · Dead code & dead tokens (dead code)

Worth exploring

Files: src/tokens/*.css, src/elements/, stories/, package.json, fonts/*.ttf

Problem

Nine tokens are defined but not read through var() anywhere in src/, stories/, or demo/:

--cf-accent-2 --cf-warning --cf-border-thick --cf-leading-tight --cf-row --cf-text-caption --cf-text-display-xl --cf-text-subheading --cf-tracking-normal

They are public interface, so they are not necessarily dead, but none of them is exercised or proven. The TTF files are unused assets.

Solution

  • knip for unused files, exports, and devDeps (entry points: exports + .storybook + stories)
  • A token-usage report that warns on tokens with no consumer and no Foundations story, and fails only on tokens absent from both
  • Drop the TTFs from files, or move them out of the package

8 · Docs integrity (readability)

Speculative

Files: README.md, AGENTS.md, CONTEXT.md, docs/adr/*

The repo is self-documenting by policy, so broken ADR cross-links or an ADR missing from docs/adr/README.md count as defects. markdownlint + lychee (offline mode for repo links) + a 10-line script asserting every docs/adr/NNNN-*.md is listed in the index. The cost is low, but the value depends on how often docs drift, and so far they haven't.

Top recommendation

Start with #1 (build & package gate), with #2 (size budget) in the same job. It covers the area where bugs have actually landed: three of the last ten commits fix the published package, and today nothing checks that package before merge. It is one new ci.yml job, it would immediately show whether the TTF/duplicate-font weight is real, and it gives #2 and #4 the built dist/ they need.

Then do #5 (supply-chain hardening). Most of it is configuration (SHA pins, permissions:, Dependabot, zizmor), and trusted publishing removes the riskiest secret this project probably has.

Suggested order: 1+2 → 5 → 3 → 4 → 7 → 6 → 8.

Solo "weekend one" bundle (≈ half a day, €0): #1 + #2 in a new ci.yml, then from #5 the configuration-only items: SHA pins, permissions:, zizmor, monthly grouped Dependabot, secret scanning on. Defer #4 (custom code to maintain) and #6–#8 until the library has its first outside consumers.
