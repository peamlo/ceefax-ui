# ADR-0002: Squash-only merges with Conventional-Commit PR titles

## Context

Commit messages are linted locally by a husky `commit-msg` hook, but nothing
validated what actually landed on `main` when a PR was merged on GitHub. The repo
had all three merge methods enabled. A **merge-commit** title is auto-generated by
GitHub (`"Merge pull request #N…"`) and can never satisfy commitlint, so "the merge
commit follows commitlint" is only achievable if we control the commit that lands.

## Decision

Merges into `main` are **squash-only** (`allow_merge_commit` and
`allow_rebase_merge` disabled), and the squash commit title is the PR title
(`squash_merge_commit_title=PR_TITLE`). The PR title is therefore the single commit
that lands on `main`, and it is validated in CI
(`.github/workflows/pr-title-lint.yml`) by piping it through the same
`commitlint.config.js` the husky hook uses — one source of truth, no rule drift.

## Consequences

- Exactly one Conventional commit lands per PR; individual WIP commit messages are
  squashed away, so CI lints the PR title only (not every commit).
- Enforcement is a **hard** gate: the repo is public, so the `main protection`
  ruleset requires the `lint-title`, `test-storybook` and `package` status checks (plus a
  pull request, no force-push, no deletion, linear history) before merge. This
  supersedes the original soft check, written while the repo was private on the
  free plan where required checks were unavailable.
- `package` (`.github/workflows/ci.yml`, issue #45) builds and packs the library
  and asserts the tarball, so packaging regressions block merge instead of
  surfacing after a release.
- Reversible: re-enabling other merge methods is a repo-settings change.
